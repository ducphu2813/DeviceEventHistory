# Device Event History - MongoDB Schema V1

> Đối chiếu implementation ngày 2026-08-26: các collection history, failure và checkpoint cùng mapper/index initializer đã có trong source Worker. Các projection/API bên dưới vẫn là hướng mở rộng, chưa phải runtime của Worker hiện tại.

## 1. Mục đích

Tài liệu này chốt định hướng MongoDB cho hệ thống lưu lịch sử sự kiện của thiết bị RFID và các thành phần liên quan.

Mục tiêu:

- Lưu lịch sử đọc thẻ và business event.
- Theo dõi trạng thái thiết bị, gate, antenna và connection.
- Hỗ trợ kỹ thuật trace lỗi theo thời gian, thiết bị, file nguồn và record gốc.
- Hỗ trợ thống kê hoạt động và tiến độ sản xuất.
- Cung cấp dữ liệu cho API monitoring, timeline, diagnostics và reporting.
- Có thể dựng lại trạng thái/tổng hợp từ lịch sử gốc.

Đây là thiết kế Schema V1 ở mức source-of-truth cho team phát triển. Các mã trạng thái và field runtime cần được kiểm chứng thêm bằng log mẫu thực tế trước production.

## 2. Vì sao chọn MongoDB

MongoDB phù hợp vì dữ liệu có các đặc điểm:

- Chủ yếu là event append-only.
- Nhiều loại event có cấu trúc khác nhau.
- Cần giữ cả raw payload và dữ liệu đã phân giải.
- Truy vấn thường theo thời gian, thiết bị, gate, tag và category.
- Projection trạng thái/thống kê có thể tách khỏi lịch sử gốc.

Nguyên tắc kiến trúc:

```
Raw event history bất biến
        |
        v
Parser / validator
        |
        +--> parsed facts
        +--> ingestion failure nếu lỗi
        |
        v
Rebuildable projections
```

Không chỉ lưu dữ liệu đã giải mã rồi bỏ raw text. Raw payload là bằng chứng để trace, đối chiếu với file và sửa parser về sau.

## 3. Phạm vi event

Collection chính có tên tổng quát là device_event_history.

| Category | Ý nghĩa | Nguồn có thể có |
|---|---|---|
| tag_read | Một lần đọc thẻ RFID | File_{FileId}.txt, reader callback |
| business_process | Process, quantity, reset, change process | raw-log te(...), ERP/application |
| device_connection | Connected, disconnected, reconnecting | RFID.Antenna, SignalR, application log |
| device_control | Bật/tắt đèn hoặc lệnh điều khiển | SignalR/API/application |
| gate_state | Trạng thái gate/user state | raw-log b(...), callback |
| sensor_state | Thay đổi sensor | device/application callback |
| device_error | Lỗi reader, callback, giao tiếp | application log, reader callback |
| ingestion_error | Worker không đọc/parse được | Device Event History Worker |
| application_error | Lỗi ứng dụng ghi/đọc log | application log |

Sáu block @(...), b(...), t(...), te(...), sp(...), u(...) chỉ là format của raw-log RFID.Antenna; không phải mọi device event đều có chúng.

## 4. Sáu block raw-log RFID.Antenna

| Block | Ý nghĩa | Dữ liệu chính |
|---|---|---|
| @(...) | Thông tin chính của record | tagId, thời gian, deviceId, gateId |
| b(...) | Trạng thái gate/user state | state code gốc |
| t(...) | Tín hiệu RFID | antenna, RSSI, phase, power, channel, count |
| te(...) | Business/process event | event type, process, quantity, process ids |
| sp(...) | Style/process tùy chỉnh | processCustom |
| u(...) | User tạo/tác động event | userId |

e(0) là marker kết thúc record để reader biết dữ liệu đã hoàn chỉnh; không xem nó là block nghiệp vụ thứ bảy.

Một record có thể chỉ có một phần block. Đọc thẻ thường có @ + b + t; business event thường có @ + te, có thể thêm sp và u.

## 5. Luồng dữ liệu

```
RFID reader / emulator / business event source
        |
        v
RFID.Antenna
        |
        +--> giải mã EPC, xác định FileId
        +--> deduplicate kỹ thuật trong thời gian ngắn
        +--> tạo raw record
        |
        v
{FolderRawData}/yyyy/MM/dd/File_{FileId}.txt
        |
        v
Device Event History Worker
        |
        +--> đọc record hoàn chỉnh đến e(0)
        +--> parse thành facts
        +--> lưu history hoặc ingestion failure
        +--> commit checkpoint sau persistence
        |
        v
MongoDB
```

Raw file không chứa mọi event của RFID.Antenna. Reconnect, lỗi ứng dụng, bật/tắt đèn hoặc connection state có thể nằm trong application log, UI/console hoặc SignalR. Muốn lưu chúng, Worker cần input adapter tương ứng.

Worker phải có checkpoint riêng, không dùng chung vị trí đọc với RFID.Analytics hiện tại.

## 6. Collection device_event_history

Đây là lịch sử chính và là source of truth.

### 6.1. Nguyên tắc

- Append-only: không sửa nội dung event gốc sau khi lưu.
- Một record nguồn tương ứng với một document.
- Luôn giữ rawPayload.
- Dữ liệu đã parse đặt trong facts.
- Field không có trong event để null hoặc bỏ qua; không điền giá trị giả.
- Projection không được ghi đè history.

### 6.3. Ý nghĩa nhóm field

| Nhóm | Mục đích |
|---|---|
| eventId | Định danh ổn định, phục vụ idempotency |
| category | Nhóm event để API filter |
| sourceKind | Event đến từ file, SignalR, callback hay application log |
| occurredAtUtc | Thời điểm event xảy ra nếu xác định được |
| receivedAtUtc | Thời điểm Worker nhận event |
| source | Vị trí nguồn để trace ngược |
| device | Thiết bị/gate liên quan |
| connection | Context kết nối nếu có |
| rawPayload | Dữ liệu nguyên bản |
| facts | Dữ liệu đã phân giải |
| parse | Kết quả parse, warning và error |
| ingestion | Thông tin Worker tiếp nhận/lưu trữ |

Không dùng FileId thay cho device.id. FileId là khóa định tuyến raw-log/host stream; device.id mới là định danh thiết bị.

## 13. Idempotency và checkpoint

Worker có thể restart hoặc đọc lại một phần file. eventId nên được tạo ổn định từ:

```
source file key + offsetStart + rawText hash
```

eventId chỉ chống ghi trùng khi persistence. Không deduplicate lịch sử bằng deviceId + tagId, vì một tag có thể được đọc nhiều lần, ở nhiều antenna và nhiều thời điểm.

Worker chỉ commit checkpoint sau khi:

1. Có record hoàn chỉnh đến e(0).
2. Record đã được lưu vào device_event_history, hoặc lỗi đã được lưu vào ingestion_failures.
3. MongoDB xác nhận persistence thành công.

## 14. Index đề xuất

device_event_history:

```
unique eventId
occurredAtUtc descending
device.id + occurredAtUtc descending
device.gateId + occurredAtUtc descending
facts.tagRead.tagId + occurredAtUtc descending
category + occurredAtUtc descending
parse.status + receivedAtUtc descending
source.sourceId + source.folderDate + source.fileId + source.offsetStart
```

ingestion_failures:

```
source.sourceId + source.folderDate + source.fileId + source.offsetStart
error.code + receivedAtUtc descending
resolvedAtUtc
```

Projection keys:

```
device_current_state: unique deviceId + gateId
tag_current_state: unique tagId
production_daily_stats: unique day + deviceId + gateId
```

Chỉ thêm index theo query và benchmark thực tế; quá nhiều index sẽ làm tăng chi phí ghi.

Implementation hiện tại mở rộng source index của history/failure với
`source.sourceId` và dùng `source.relativePath` trong checkpoint unique key để
không trộn hai Antenna installation hoặc hai stream có cùng `FileId`.

## 15. Retention và API

V1 hiện không tự động xóa raw history và `MongoIndexInitializer` chưa tạo TTL
index; các option retention mới là cấu hình nền cho chính sách sau này. Có thể
archive dữ liệu cũ hoặc dùng `expireAtUtc` khi chính sách lưu trữ được chốt.

API dự kiến:

```
GET /api/device-events
GET /api/device-events/{eventId}
GET /api/devices
GET /api/devices/{deviceId}/timeline
GET /api/devices/{deviceId}/current-state
GET /api/tags/{tagId}/timeline
GET /api/ingestion/failures
GET /api/production/daily-stats
GET /api/ingestion/health
```

device-events nên filter theo from, to, deviceId, gateId, tagId, category, sourceKind và parse.status. Timeline đọc history; current state đọc projection; thống kê đọc projection tổng hợp.

## 16. Nguyên tắc triển khai Worker

```
Source adapter
    ↓
Raw event envelope
    ↓
Bounded buffer
    ↓
Parser / validator
    ↓
History repository hoặc failure repository
    ↓
Checkpoint repository
    ↓
Projection updater
```

- Không thực hiện MongoDB write nặng trực tiếp trong callback SignalR.
- Không update projection trước khi history persistence thành công.
- Khi buffer đầy phải có metric và health signal; không silently drop.
- Lưu parserVersion và schemaVersion.
- Có metric cho record đọc, parse thành công, parse lỗi, retry, persistence failure và ingestion lag.

## 17. Những điểm cần kiểm chứng trước production

- Ý nghĩa đầy đủ của numeric code trong b(...) và te(...).
- Múi giờ và độ chính xác của thời gian raw record.
- Mapping chính thức giữa DeviceId, GateId, CompanyId và tenant.
- Danh sách application log/SignalR event cần ingest.
- Cách xác định chính xác process hoàn thành.
- Retention, archive và dung lượng event thực tế.

Khi chưa đủ bằng chứng, giữ raw payload và để field chuẩn hóa là null thay vì suy đoán.

## 18. Definition of Done Schema V1

- Có document mẫu cho tag read, business event, connection event và error event.
- Parser giữ nguyên raw payload.
- Mỗi event có idempotency key ổn định.
- Worker không commit checkpoint quá sớm.
- Event lỗi được lưu vào ingestion_failures.
- Có index cho query monitoring chính.
- Có projection current state tách khỏi history.
- Projection rebuild được từ history.
- API truy vấn được timeline theo device, gate và tag.
- Có metric/health cho ingestion lag, parse failure và persistence failure.
- Đã kiểm chứng bằng sample log thực tế của môi trường mục tiêu.

## 19. Tóm tắt

```
device_event_history
    = lịch sử gốc, không sửa, có raw payload

ingestion_failures
    = event lỗi để kỹ thuật điều tra

ingestion_checkpoints
    = Worker đã đọc đến đâu

device_current_state
    = trạng thái mới nhất của thiết bị

tag_current_state
    = tiến độ mới nhất của tag/process

production_daily_stats
    = số liệu tổng hợp để báo cáo
```

Thiết kế này giúp hệ thống vừa giữ được bằng chứng gốc để trace, vừa có dữ liệu đã phân giải cho API, vừa có thể xây dựng dashboard/thống kê mà không mất khả năng rebuild hoặc điều tra lại lịch sử.
